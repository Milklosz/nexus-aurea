# Session Manager 2.0

## Implementation

`velora_session_manager.rs` is a bounded, sanitized projection of the existing LaunchRegistry. It does not add a competing lifecycle registry, process watcher, persistent window handles or restart loop. Registry events and window-focus notifications refresh the panel; inventory is also manually refreshable. The existing registry watcher owns exit/crash reconciliation. Up to 20 retained sessions are projected with launch ID, fixed application identity/name, application type, sanitized launch adapter family, lifecycle state, launch timestamp, latest observation timestamp, actual observed last activation timestamp, capabilities and a generic recoverable failure.

`lastActivationAtMs` is nullable and belongs to the authoritative LaunchRegistry. The watcher records it only on foreground entry of an exact window whose process creation time matches the captured owner. Repeated observations, snapshot reads, session selection and denied activation requests do not move it. Recycled PIDs and broad process-name matches cannot establish an activation. It is an observed application activation, not playback progress or the exact instant Windows changed focus. Adapter families are `ownedBrowserWindow`, `steamClient`, `gameLauncher`, `playniteClient` and `managedExecutable`; no paths or command arguments are exposed. The generic game family deliberately does not infer Steam from every possible game identity.

Foreground, observed activation and owned-window changes notify the existing `velora-launch-event` subscribers even when the lifecycle phase remains `sessionActive`. Stable watcher ticks emit no additional event. This prevents a Control Center focus refresh that runs before the next native observation from leaving session labels and ordering stale until manual refresh.

States distinguish launching, running, foreground, background, unavailable, exited and failed. The snapshot separately includes fixed Home application identities with `notRunning` and a null session ID when there is no VELORA-managed launch. The panel discloses these under “Pozostałe aplikacje”; it never fabricates Resume actions, assumes installation availability, or claims that unrelated application processes are stopped. Normal launch actions remain on Home. A retained terminal launch cannot hide a live unavailable or background session. Missing/recycled owners and pending exits suppress Resume. A live HWND owner must match captured process ID **and process creation time**. IPC accepts a bounded launch ID, never HWND/PID, shell text or a URL. Resume reuses the existing orchestrator selection transaction and WindowBroker's exact-owned activation check. Windows focus refusal is an error, not successful resume. No new window is launched by Resume.

Close requires explicit confirmation and delegates the existing Edge Cinema close adapter. That adapter validates the selected service marker, current active launch, exact window and captured identity before posting WM_CLOSE to one owned window. Other applications do not expose Close. A close receipt reports a request; only the native watcher can subsequently report termination. No browser processes are killed. Streaming video timestamps, account data, private window titles and arbitrary native errors are not projected.

After an accepted close request, the panel observes existing registry updates and schedules one delayed read at 6.5 seconds, beyond the native five-second exit grace. A supported snapshot showing the selected session exited or no longer retained confirms session termination. An active, unavailable or unconfirmed result replaces the request notice with “Nie potwierdzono zamknięcia okna” and offers “Sprawdź okno” through the existing exact-owned Resume action when available. The warning is shown at the deadline even if the confirmation read stalls. A failed/unsupported read never proves closure. The panel does not repeat WM_CLOSE, kill a process or add recurring polling. A newer action or unmount cancels the timer; action generations discard stale asynchronous notices. Later native termination events can still resolve the warning.

`SessionsPanel` uses accessible native buttons and the existing `data-remote-allow` route. Controller/remote input reaches the same controls through the application's current focus router; physical behavior remains unverified. The user sees a second confirmation before closing a service. No additional network endpoint is added.

## Integration

Register module `velora_session_manager` and commands `get_managed_sessions`, `resume_managed_session`, `close_managed_session` in `lib.rs`. Place `<SessionsPanel />` in Control Center. Frontend service: `src/services/veloraSessionManager.ts`.

## Verification and limits

Tests cover stale/terminal lifecycle, PID-reuse suppression, observed activation timing, stable-event coalescing, no invented idle sessions, diagnostic redaction, malformed IDs, exact IPC payloads, browser preview refusal, focus denial and explicit close confirmation. Targeted verification after these additions: LaunchRegistry 28/28 and session projection 6/6 native tests passed; frontend session/controller tests 12/12 passed. Live Windows session switching and unrelated-window preservation require separate Computer Use evidence in `velora-2-grand-computer-use-results.md`. Physical controller and iPhone validation are deferred. This feature resumes application windows, not streaming content or game save state. Session metadata remains owned by existing registry/storage; no second persisted session file is introduced.
