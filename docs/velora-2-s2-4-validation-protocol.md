# S2.4 Windows validation protocol

Protocol date: 2026-11-17 (Europe/Warsaw). Candidate version: **0.12.0-rc.1**. This is an executable test plan, not a results report. Record actual results separately with status **PASS / PARTIAL / FAIL / BLOCKED / NOT TESTED**. Never convert a planned step or mocked test into an observed result.

## Preflight and evidence rules

Before testing, record MSI model, Windows build, connected displays, resolution/refresh/scaling, repository branch and source SHA, executable path/version/hash and build provenance. Distinguish the isolated debug candidate from installed VELORA. Close an installed instance normally only when necessary for the shared single-instance identity; do not overwrite or install the candidate. Record the installed executable hash before and after. Avoid retaining personal account data, window titles containing private content, IP addresses or full accessibility trees in public evidence.

Use supported read-only Windows APIs for display/audio inventory. Do not change global DPI, refresh rate, HDR, audio output, shell/startup, browser security or Steam Input settings. If an alternate display mode, cable reconnection or physical controller is necessary, leave that subtest BLOCKED until separately authorized/performed. Continue independent tests.

Open the candidate's F2 diagnostic panel and enable native Home and the local debug simulator through their existing explicit controls. Capture one owned service session. The simulator shares the normalized native route; it does not prove raw DS4/Bluetooth input. Read [simulator instructions](velora-2-s2-4-controller-simulator.md) before replay.

Each scenario record must identify:

- build SHA and EXE SHA-256, time, display/DPI context and service surface (public, authenticated catalog, player, modal or ad);
- initial focus/session/mode, semantic actions in order, native sequence/generation, ownership, diagnostics/fallback and dispatch result;
- observed UI effect after each important action, screenshots or sanitized observations where appropriate;
- ordinary Computer Use intervention and any manual refocus, typing, session repair or unreported prerequisite;
- final status, exact failed/blocked step and reproducible next action.

**Input provenance:** Computer Use clicks on simulator buttons, mode/session selectors and local review checkpoints are allowed ways to produce simulated actions. Mouse clicks, scrolling, typing or keyboard shortcuts inside a service are ordinary Computer Use intervention. Record them as setup/intervention; they invalidate a claim that the affected end-to-end segment was completed using only simulator actions. A title selected by ordinary mouse and then paused by the simulator demonstrates a narrower pause test, not controller-only title selection.

**Effects:** Windows/native acceptance is a command receipt. Playback, focus movement, selection, scroll, Home completion and fullscreen require observation. Operator annotations are separate from native receipts. Home continuation requires native completion/focus readiness; it must not advance merely because the Home worker accepted a queued request.

**Current replay boundary:** real Home closes diagnostics. S2.4 deliberately stops the current segment, retains bounded sanitized in-process receipts/recording/remaining steps, and requires reopening diagnostics plus explicit Resume after native readiness. There is no hidden input runner. Report automatic multi-service replay as PARTIAL even when all explicit segments succeed; distinguish this limitation from service-page ordinary CUA intervention.

Use only legitimate public content or already available authorized sessions. Do not enter/capture credentials, automate authentication dialogs, bypass DRM/security/ads, or trigger purchases, rentals, subscriptions or account changes. If authentication is absent, protected catalog/player substeps are BLOCKED; public-page results remain separately scoped. Review every replayed activation/media checkpoint before continuing.

## Result classification

`PASS` means the stated scope and visible effects were observed on the identified build. `PARTIAL` identifies completed substeps and missing evidence/intervention. `FAIL` records a reproducible incorrect/rejected effect for the intended scenario; a fail-closed security behavior can pass its security criterion while navigation remains failed. `BLOCKED` names a real missing dependency (authentication, physical event, unavailable display/tool). `NOT TESTED` means no S2.4 runtime attempt/evidence yet.

The [compatibility matrix](velora-2-s2-4-compatibility-matrix.md) uses VERIFIED/PARTIAL/FAILED/BLOCKED/UNSUPPORTED/NOT TESTED per capability. Its VERIFIED entries must link the corresponding runtime record, not just the protocol or source file. Retain S2.3 results as historical comparison; never copy them into S2.4 acceptance without retesting.
