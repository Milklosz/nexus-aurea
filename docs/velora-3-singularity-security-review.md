## 2. Method

- Full read of the remote-access trust path (pairing, hello, command authentication, replay classification, rollback), the LAN HTTP server (routes, middleware, TLS, bind address), the credential/state-lock layer, and the portable isolation layer.
- Targeted reads + greps for every named attack surface: window targeting (`FindWindowW`/`SetForegroundWindow`/`OpenProcess`/`TerminateProcess`/global hooks/input synthesis), process launching (`Command::new`, `ShellExecuteW`, `steam://`, `playnite://`), URL allowlists, untrusted file parsing (session marker, Playnite manifest, VDF), diagnostics redaction, CI triggers/permissions/artifact identity, retry loops, IPC contract drift tests, lockfile diffs vs `main`.
- No test suites were executed (expensive); conclusions rely on the in-repo unit/integration tests that pin the invariants (quoted below) plus direct code reading. Quoted line numbers refer to base `8ed616a`.

## 4. Answers to the 20 review questions

1. **Can input events be duplicated?** — **No (verified).** Remote commands are serialized by `command_gate` and the cross-process state lock, and the sequence is durably reserved *before* the side effect (`remote_access.rs:1524-1540` "Reserve before the side effect"); `classify_replay` (`remote_reliability.rs:302-321`) acknowledges only an exact `(sequence, command)` receipt and treats equal-sequence-without-receipt as `Ambiguous` (409, never re-executes). Controller reports dedupe on emitted-state change (`ds4.rs:475+`, `pad.emitted` diff) with `DUPLICATE_REPORT_WINDOW_MS = 8` (`gamepad_home.rs:17`); background `State` events are filtered (`pad_hub.rs:297`), and the foreground-gain re-send (`pad_hub.rs:437-445`) reports only what was *not* delivered while background. Streaming queue drops packets older than `STALE_PACKET_MS = 200` (`streaming_control.rs:23,1032`).
2. **Can stale controller input activate commands?** — **No (verified).** `PAD_STALE_MS = 3_000`, `SILENCE_RELEASE_MS = 750` release held directions on report gaps (`ds4.rs:41-45`); chord state resets after `DEVICE_STALE_MS = 5_000` (`gamepad_home.rs:16,296-299`), requires a fully neutral sample after reconnect/gate change (`gamepad_home.rs:330-343` `awaiting_neutral` / `neutral_generation`), enforces `CHORD_WINDOW_MS = 250` and `COMBO_COOLDOWN_MS = 750` with a latch (`:354-375`); queued streaming packets older than 200 ms are dropped (`streaming_control.rs:1032`).
3. **Can Home recovery target the wrong window?** — **No (verified).** `restore_velora` → `request_foreground(own_window)` only ever calls `SetForegroundWindow` on VELORA's own validated HWND (`window_broker.rs:1053,1605-1616`); the decision `evaluate_restore` (`:287-335`) blocks any unidentified/foreign foreground and allows a device Home only when the foreground process is one VELORA launched, with PID+creation-time anti-recycle via `foreground_belongs_to_ended_session` (`:427-439`). Window close/activate paths validate HWND + PID + creation time (`activate_owned_window`/`close_owned_window`, `:1560-1603`). Second-instance activation uses `FindWindowW` with the portable-distinct title (`single_instance.rs:43-69,117-133`; `portable.rs:33-34`). Edge adoption requires the marker's PID+creation time to match the tracked launch (`edge_cinema.rs:484-494,1881-1929`).
4. **Can session generations become inconsistent?** — **No (verified).** Session revisions are monotonic; a stale `expected_revision` is rejected before mutation (`session_orchestrator.rs:1571-1580` test, `:543-556` stale-generation guard); superseded Home requests are rejected (`home_request_is_superseded`, `:260`, `:931-943`); launch `app_generations` reject stale generations "never replayed" (`launch_registry.rs:~530` comment + sidecar); streaming `generation`/`epoch` bump only on real transitions and workers compare them (`:1040-1056`, `streaming_control.rs`).
5. **Can streaming transitions replay unsafe actions?** — **No (verified).** Real transitions call `invalidate_controller_streaming` and bump the generation exactly once; deduped/stale commands produce no changed event and do not bump it (`session_orchestrator.rs:543-556,1999-2058` tests); the worker drops packets whose `queued_at` age exceeds `STALE_PACKET_MS` (`streaming_control.rs:1032,1917,2264,2362`); remote navigation re-validates the owned foreground streaming target and generation (`route_remote_navigation`, `:1455-1500`).
6. **Can Steam launches target unexpected applications?** — **No (verified).** `is_valid_appid` accepts only 1–10 ASCII digits parsing to a positive u32 (`steam_library.rs:78-83`); the appid must exist in the scanned, installed library (`:499-505`); the URI is built as `steam://run/<digits>` so no URI injection is possible, opened via `ShellExecuteW` (`open_steam_run_uri`, `:566-592`); the `-applaunch` path uses `appid_from_game_id` with the same validation (`app_manager.rs:560-600`). Steam library reading is strictly read-only VDF/registry (module doc `:1-10`).
7. **Can game process monitoring affect unrelated processes?** — **No (verified).** Monitoring is read-only Toolhelp snapshots (`process_table.rs:127-175`); game watches match descendants of the captured root with a pre-launch baseline and excluded helper images (`launch_registry.rs:449-489,642-670`); identity requires PID **and** creation time (`process_table.rs:98-105`); close paths send `WM_CLOSE` only to identity-validated owned windows and explicitly never kill processes (`window_broker.rs:889-925`, `edge_cinema.rs:1019-1060`, `request_edge_cinema_close` `:1022-1070`; `grep TerminateProcess` across `src-tauri/src` → zero hits). `cancel_launch` only releases tracking (`:1834-1872`). Residual (INFO): name-based (non-descendant) app watches could *attribute* a user-started same-name process to a session, but the only effect is observation, since closes are identity-bound.
8. **Can remote commands bypass authorization?** — **No (verified, fail-closed).** Every `/api/command` POST must pass Host+Origin middleware (`:2460-2490`), JSON content-type, 4 KiB body cap (`:1091`), HMAC-SHA256 over `NEXUS-AUREA-REMOTE-V1\n{device}\n{seq}\n{cmd}` with the per-device token (`verify_command_signature`, `:510-524`), re-verified on a fresh store read under the cross-process lock (`:1486-1503`), sequence freshness + rate limit + replay classification (`:1504-1547`); unknown device / bad signature / disabled server → 401/503 before any side effect. Native actions are a fixed allowlist — "the phone never supplies keys, HWNDs or processes" (`:1597-1599`). Pairing itself requires the enabled server + single-use 60 s code + rate limit (`:1334-1398`). The unauthenticated surface is exactly `/api/status` (counts only). Frontend additionally gates remote `select` behind `data-remote-allow`/`data-remote-admin`/`data-velora-confirm` (`src/services/remotePermissions.ts:1-45`).
9. **Can TLS validation be weakened?** — **No (verified).** The LAN server uses `axum_server::tls_rustls::RustlsConfig::from_pem` with a leaf cert signed by the vault CA, SAN = the private IP only, 90-day validity (`:1009-1089`); there are no `danger_accept_invalid_certs`/`invalid_hostnames` literals — pinned by test `phase3_no_alternate_transport_or_weak_tls_literals_in_the_lan_server` (`:3148-3168`); the server binds only to a **private** IPv4 (`local_remote_address`, `:1727-1748`, `is_private()` check). Clients must install/trust the generated CA profile first (`start(..., trust_confirmed)` refuses otherwise, `:1017-1020`).
10. **Can pairing tokens leak into logs?** — **No (verified).** `remote_access.rs`, `remote_reliability.rs`, `credential_store.rs`, `diagnostics.rs` contain no `log::`/`tracing::`/`println!` calls at all (grep → 0 hits); the PWA never `console.log`s and zeroes the token bytes after pairing (`public/remote/app.js:655`), stores the HMAC key only in origin-scoped IndexedDB (`:233-274`), and clears the `#pair=` URL fragment immediately without ever sending it (`:104-123`); the pairing code reaches the LAN only inside the single-use `/api/pair` body, never via `/api/status` (`:2553-2567`). Diagnostics explicitly exclude pairing credentials (`:69`, `:149`) and a test pins it (`:682`).
11. **Can portable mode access installed credentials?** — **No (verified).** Portable mode switches the Credential Manager **service namespace** to `com.nexus.aurea.remote.portable-validation` (`portable.rs:20-24,27-28,45-47`, consumed at `remote_access.rs:435`), a disjoint mutex (`portable.rs:30-31`) and a disjoint window title; `trust_profile_dir` in portable mode never even receives the installed Downloads path (`remote_access.rs:586-611`); `resolve_trust_profile_dir` routes portable writes under the portable data root only (`:599-612`); `cleanup_trust_artifacts` refuses unless the path is inside the portable root (`:963-968`); autostart writes are refused in portable mode at the only system-writing command (`autostart.rs:130-137`); `lib.rs:57-64` redirects all Tauri app dirs (incl. WebView2 data) into the portable root; the launcher scripts only set process-local env vars and never touch the registry/installed data (`scripts/portable/Start-VELORA-Portable.ps1:22-46`). Note (INFO): both builds run as the same Windows user, so isolation is namespace-based by design, and it holds in code.
12. **Can diagnostics expose sensitive information?** — **No (verified).** `capture()` builds a typed snapshot that deliberately excludes device names, origins, pairing credentials and certificate paths (`diagnostics.rs:69`); `sanitize_snapshot` + `sanitize_text` redact `C:\Users\…` whole-line, control characters, and `token=`/`secret=`/`password=`/email-like patterns (`:256-370`); export is capped at 256 KiB and returned as JSON with a SHA-256 (`:21,477-499`); tests pin "never contains secret material or raw window titles" (`:682,747`). Edge-cinema projections never fabricate `window_title` (`edge_cinema.rs:352-356`).
13. **Can a retry loop become unbounded?** — **No (verified).** Backend `RetryPolicy::should_retry`/`next_delay_ms` is bounded by `max_attempts` with capped exponential backoff (`remote_reliability.rs:106-137`); frontend `planRetry` defaults to `maxAttempts=3`, treats `ambiguous`/unknown as never-retryable, and `remoteReliability.ts:481` clamps to ≤8 (`retryPolicy.ts:22-24,81-107`; `remoteReliability.ts:471-499,822-825`). The queue drain `while (queue.size() > 0 && online)` (`:928`) consumes each item once; ambiguous timeouts require explicit re-confirmation with identical signed bytes (`:721-724` test, `app.js:734-795`).
14. **Can an IPC contract drift silently?** — **No (verified).** `IPC_COMMANDS` is the single typed registry with `isIpcCommandName`/`ipcDescriptor` guards (`src/contracts/ipc.ts:27,283-307`); `src/__tests__/genesisEIntegration.test.ts:88-115` enforces both directions against the `generate_handler![...]` block in `lib.rs` (every contract command registered; every new handler documented; no duplicates; base set from `ded73f4` never removed), run in CI via `pnpm test:genesis` (`ci.yml`).
15. **Can a failed background task leave corrupted state?** — **No (verified).** Session state is written temp-file + `sync_all` + rename, size-capped, version-checked, and the reader treats truncation as corrupt and falls back safely (`session_store.rs:40-100`); credential state uses the fail-closed cross-process byte-range lock with a verified checkpoint (`remote_state_lock.rs:1-30,94-121`, `remote_access.rs:2131-2180`), persist-before-emit for command sequences, and a compare-and-swap rollback that can only lower a sequence if the stored value is still the reserved one (`:1549-1567`); a failed write leaves the cache untouched and the next command re-reads (`:1530-1536`).
16. **Can CI publish an artifact from the wrong commit?** — **No (verified).** `ci.yml` has top-level `permissions: contents: read`; `publish-release` runs only on `push` to `refs/tags/v*` with `contents: write`, downloads the artifact named `VELORA-Windows-x64-${{ github.sha }}`, and runs `scripts/build-provenance.mjs verify-release` which requires the manifest to belong to this run's commit/event/tag (`:` "Select and verify release assets" step). The build job writes/verifies a provenance manifest with `--ci` against the GitHub context, extracts the NSIS payload and allows exactly one packaged EXE. `portable-windows.yml` checks out `pull_request.head.sha` explicitly and refuses a dirty checkout (`git rev-parse HEAD` comparison). No `pull_request_target` anywhere; no `secrets.*` usage (grep → 0 hits).
17. **Can the installed VELORA be overwritten accidentally?** — **No (verified).** The portable workflow builds with `--no-bundle` (never produces/runs an NSIS installer) and packages a ZIP + SHA-256 manifests; portable scripts never install or write the registry; portable mode refuses autostart writes and uses disjoint credential/mutex/window identities (see Q11); the single-instance activation cannot target the installed window from the portable build because the title differs (`single_instance.rs:12-13`, `portable.rs:33-34`).
18. **Can UI state claim a capability that does not exist?** — **No (verified).** `focus_restore_supported` is an honest per-app flag (only Playnite true; Steam/browsers/Apple Music false — `app_manager.rs:104-150`); `PLAYBACK_STATE_READ_SUPPORTED = false` (`streaming_control.rs:38`, pinned by test `:3301`) and the Home UI fabricates no playback progress (`src/services/homeSections.ts:25`); `window_title` stays `None` instead of being fabricated (`edge_cinema.rs:352-356`); foreground denials are reported as `unknown`/`BlockedByWindows`, never masked (`window_broker.rs:197-211`, `diagnostics.rs:147`); non-Windows snapshots are honest stubs (`display_audio.rs:1839`, `steam_library.rs:844`).
19. **Can protected streaming state be falsely represented?** — **No (verified).** With `PLAYBACK_STATE_READ_SUPPORTED=false`, playback state is never read or invented; DRM/protected-content errors map to an honest notice (`src/services/edgeCinema.ts:78`, `edgeCinemaLifecycle.ts:186`); streaming quiescence is emitted with the real generation (`session_orchestrator.rs:587-608`); persisted session state never carries receipts or playback state (`session_store.rs:209` test).
20. **Can the application fail without actionable diagnostics?** — **No (verified).** `diagnostics.rs` collects per-subsystem errors (session persistence, launch registry, window broker, control service, controller, display/audio, remote store health) plus explicit `limitations` and surfaces remote recovery options (`capture`, `:155-252`); autostart has a recovery report (`autostart.rs:500-523`); remote store faults have a local, one-time-token recovery plan (`remote_access.rs:1192-1320`); monitor threads join with a bounded 2 s timeout so exit can't hang (`window_broker.rs:1078-1105`); lifecycle marks clean shutdown before exit/restart (`lifecycle_control.rs:5-15`). The only fail-open spot found is F2 (single-instance mutex), which starts normally rather than failing silently.

## 5. Verified-safe controls (checked and found intact)

- **Fail-closed remote access:** disabled server → 503; unknown device / bad HMAC / stale sequence → 401; store unreadable → 503 and no unprotected write (`remote_access.rs:1451-1547`, `remote_state_lock.rs:114-121`, `remote_access.rs:430-449`).
- **HMAC-SHA256 command authentication** with constant-time `verify_slice`, bound to device id + monotonic sequence + command string (`:510-524,1486-1503`); signed hello reuses the same key, exposes only counts and a nonce-bound ack (`:1401-1449,2431-2450`).
- **Replay protection, persist-before-emit:** sequence reserved durably before the side effect; receipts acknowledge only exact duplicates; ambiguous → 409; rollback is CAS-only (`:1512-1567`, `remote_reliability.rs:302-321`).
- **TLS:** rustls from the vault CA PEM only, SAN=private IP, no weak-TLS literals (test-pinned `:3148-3168`); private-IPv4-only bind (`:1727-1748`); Host+Origin middleware, JSON-only POSTs, 4 KiB body cap, `no-store`/`nosniff`/CSP headers (`:2460-2517`).
- **Route/command allowlists:** exactly 11 LAN routes (test-pinned `:3107-3122`); 15 `RemoteCommand` variants, server-side enum is the authority; frontend re-validates event payloads with `isRemoteCommand` (`src/services/remoteCommand.ts:14-31`); edge-cinema URL allowlist is exact-match on 5 official HTTPS URLs with near-miss/injection rejection tests (`edge_cinema.rs:40-77,397-399,1418-1489`); `opener:allow-open-url` capability scoped to the same hosts + `playnite.link` (`capabilities/default.json`).
- **Pairing bootstrap expiry:** 60 s monotonic `Instant` TTL, single-use slot cleared on success, 6-digit code behind rate limit + enabled-server requirement (`:25-28,704-713,1361-1364`) — see F1 for the hardening note.
- **Credential isolation:** per-service Credential Manager namespace (portable gets a disjoint suffix), UTF-16-aware 2400-byte cap, cross-process lock around every native call (`credential_store.rs:5-8,64-95`, `portable.rs:27-47`).
- **Cross-process state lock:** fail-closed byte-range lock under the user profile, OS-released on crash, not squattable, no `Global\` (…`remote_state_lock.rs:1-30`).
- **No `TerminateProcess`, no global hooks, no input synthesis:** zero hits for `TerminateProcess`/`SetWindowsHookEx`/`SendInput`/`keybd_event` in `src-tauri/src`; window ops are `SetForegroundWindow`/`PostMessageW(WM_CLOSE)` only on identity-validated owned windows; `OpenProcess` uses `PROCESS_QUERY_LIMITED_INFORMATION` only (`control_service.rs:551,1012`, `process_table.rs:214-226`, `window_broker.rs:1300-1301,1523,1557,1576,1616`).
- **Read-only Steam/Playnite:** VDF/manifest parsing only; launches go through validated `steam://run/<digits>` / canonical `playnite://playnite/start/<guid>` URIs that must match the manifest (`:473-592`, `playnite_manifest.rs:527-556`).
- **Untrusted metadata parsing bounded:** session marker ≤4 KiB, symlink-rejected, schema+allowlist validated (`edge_cinema.rs:30-32,468-560`); Playnite manifest ≤32 MiB, ≤10 000 games, control-char/ID/timestamp validation (`playnite_manifest.rs:28-32,156-330,407-416`).
- **Honest capability flags:** `PLAYBACK_STATE_READ_SUPPORTED=false`, per-app `focus_restore_supported`, no fabricated window titles or playback state (see Q18/Q19).
- **Diagnostics redaction:** typed snapshot + path/secret/control-char scrubbing + size cap (see Q12).
- **CI hygiene:** least-privilege permissions, no `pull_request_target`, tag-only publish, SHA-named artifacts, provenance manifest verified against the run, pinned PR-head checkout with dirty-tree refusal (see Q16).
- **Portable isolation:** disjoint credential service / mutex / window title / data root; no installer, no registry writes (see Q11/Q17).
- **Autostart:** HKCU `Run` only, fixed value name `VELORA`, quote/newline stripped from the command value, absolute `%SystemRoot%\System32\reg.exe`, explicit portable refusal (`autostart.rs:12-18,63-95,128-137,532-544`).
- **Filesystem scopes:** trust profile confined to Downloads (installed) or portable `trust\` dir; lock files under `LOCALAPPDATA\VELORA\locks`; session state under `app_data_dir`, temp+rename (see Q11/Q15).
- **Bounded retries everywhere** (backend policy + frontend `planRetry`, ambiguous never retried; streaming queue drops >200 ms packets) — see Q13/Q5.
- **IPC drift tests** enforce contract ⇄ handler parity in both directions (see Q14).

## 6. Overall verdict

**PASS (no HIGH, no MEDIUM; 3 LOW hardening notes, 2 INFO).** The integrated Genesis codebase at `8ed616a` holds up under adversarial review: the LAN remote is fail-closed with HMAC + monotonic persisted sequences + replay receipts, TLS is rustls-only from a pinned private-IP CA, URL/command/process-launch surfaces are allowlisted and identity-bound, portable mode is genuinely namespace-isolated from the installed build, diagnostics are redacted, CI cannot publish a mismatched artifact and never uses `pull_request_target`, and retry/state-write paths are bounded and crash-safe. The LOW findings (pairing-code strength, single-instance fail-open, new dependency surface without an audit gate) are recommended hardening, not blockers.
